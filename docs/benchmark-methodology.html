Benchmark Methodology & Reproducibility

Complete technical specification for all Nyx performance results — hardware, compiler flags, warmup, variance, and third-party reproduction instructions.

⚠️ Measurement Context: All performance figures in Nyx documentation are internal measurements from the Nyx test environment on specific hardware (see B1 below). They are workload-specific and have not yet been independently audited or reproduced on external hardware. We publish this methodology page so that any engineer can reproduce the results and verify our claims.

The 15 Reproducibility Data Points

The external technical assessment identified 15 data points that every credible benchmark must publish. Here is our current status against each:

  • ✔
    B1 — CPU Model & Clock: Intel Core i7-6700HQ @ 2.60 GHz (Skylake, 4 cores / 8 threads, 6 MB L3 cache). Note: this is a 2015 mobile laptop CPU. Results on modern desktop/server hardware will differ, likely favourably for Nyx's region model due to larger LLC.
  • ✔
    B2 — Compiler Version: nyxc 0.27.0 (LLVM 19.1.0 backend). Rust: 1.97.0 (2025-07-01). GCC: 14.2.0. Node.js: 22.4.0 (V8 12.7). Python: 3.13.0. PHP: 8.3.6.
  • ✔
    B3 — Compiler Flags: Nyx: -O3 --lto --target-cpu=native. Rust: -C opt-level=3 -C lto=fat -C target-cpu=native. C: -O3 -march=native -flto. All languages compiled with full optimisation and link-time optimisation enabled.
  • ✔
    B4 — Benchmark Source Code: All 7 benchmark programs published at github.com/9jaoncloud/nyxos/benchmark. Includes .nyx, .c, .rs, .py, .js, .go sources and a HOW_TO_RUN.md reproduction guide.
  • ✔
    B5 — Dataset / Workload Definition:
    • Startup: process launch with no-op main()
    • Sequential alloc: 8,388,608 × 20-byte structs
    • Random alloc: 8,388,608 structs with Xorshift64 stride access (non-cryptographic PRNG, used solely to defeat L1/L2 prefetcher bias)
    • HashMap: 1,000,000 string key → u64 value insertions + 1,000,000 lookups
    • JSON: twitter.json (631 KB) parsed 100 times
    • N-Body: 50,000 orbital simulation steps, 5 bodies
    • GEMM: 512×512 double-precision matrix multiply, 10 iterations
  • ✔
    B6 — Warm-up Procedure: 1 unmeasured warm-up iteration (eliminates cold disk cache and page table fault overhead). All reported times are from post-warmup runs only.
  • ✔
    B7 — Iteration Count: 5 measured iterations per experiment. Results reported as Mean (μ) and Sample Standard Deviation (±σ). See B8.
  • ✔
    B8 — Variance / Error Bars: All tables report Mean ± σ across 5 runs. Example: Random alloc Nyx: 12.70 ms ± 0.18 ms. Raw per-run CSV available for download below.
  • ~
    B9 — Memory Consumption: Peak RSS reported for allocation experiments. For other workloads (JSON, N-Body, GEMM) RSS measurement is pending — to be added in the next benchmark update.
  • ~
    B10 — Allocation Count: Total allocation count logged via the region allocator instrumentation hook for Nyx experiments. For C/Rust/Go allocations, malloc_count is pending.
  • ✗
    B11 — Cache Misses: Not yet measured. Planned: perf stat -e cache-misses,cache-references across all workloads. Will be added in next release.
  • ✗
    B12 — Branch Misses: Not yet measured. Planned alongside B11.
  • ~
    B13 — Binary Size: Nyx binaries: hello = 34.2 KB, HTTP server = 187 KB, full NyxOS unikernel = 4.8 MB. Comparison binary sizes for Rust/C counterparts pending.
  • ✔
    B14 — Single-Thread Performance: All allocation and N-Body benchmarks are single-threaded. This is stated explicitly in the benchmark source and documented in HOW_TO_RUN.md.
  • ✗
    B15 — Multi-Thread Scaling Curve: Not yet measured. Multi-threaded scaling (1→8→16→32→64 threads) is on the roadmap for the next benchmark release, specifically for the region arena isolation model.

Reproduction Instructions

Step-by-Step on a Clean Machine

# 1. Clone the public benchmark repository
git clone https://github.com/9jaoncloud/nyxos.git
cd nyxos/benchmark

# 2. Read the reproduction guide
cat HOW_TO_RUN.md

# 3. Install required compilers
#    - nyxc: download from https://nyx.9jaoncloud.com.ng/downloads/
#    - Rust: curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
#    - GCC: apt install gcc (Linux) or use MSYS2 (Windows)

# 4. Run all benchmarks
python run_benchmarks.py --all --iterations 5 --warmup 1 --output results.csv

# 5. View results
python run_benchmarks.py --report results.csv

If you reproduce our results or find discrepancies, please open an issue on the GitHub repository. We welcome external validation — positive or negative.

Matched-Algorithm Comparisons

The external assessment correctly noted that benchmarks comparing different algorithms in different languages measure implementations, not languages. For HashMap, GEMM, and JSON we publish matched-algorithm pairs:

ParameterNyx implementationRust implementation
Hash algorithmFxHash (non-cryptographic multiplicative)FxHash (via rustc-hash crate)

Load factor0.875 max before resize0.875 max before resize

AllocationRegion bump (Nyx)jemalloc (default)
Result (mean, 5 runs)116.20 ms156.80 ms

Same algorithm, same hash function, same probing strategy. The 1.35× win is attributable to the region allocator eliminating malloc fragmentation and lock contention, not to algorithmic advantage.

Known Limitations & What We Cannot Claim

  • Results are from one hardware platform. We encourage reproduction on diverse hardware.
  • Multi-threaded scaling has not been measured (B15 open).
  • Cache miss and branch miss profiles are not yet published (B11, B12 open).
  • No independent third-party has reproduced these results yet (A1 open). We actively welcome this.
  • The 17.2× random-allocation speedup is a best-case scenario for region memory (non-linear access pattern specifically chosen to stress allocator latency). It does not represent typical application speedup.
  • N-body (12.36 ms vs C 11.76 ms) and JSON (24.25 ms vs simdjson 12.40 ms) show Nyx is not fastest in compute-bound workloads — we report these honestly because a language that wins everything is unbelievable.
